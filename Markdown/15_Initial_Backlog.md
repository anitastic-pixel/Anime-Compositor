# Implementation backlog and task briefs

Version 0.3 | 2026-09-04 | Accepted for baseline

## Backlog rules

All tasks are NOT STARTED. Sequence reflects dependencies, not calendar. Every task attaches a verification artifact per document 12 before it closes. A task without an artifact the owner has reviewed is not done, regardless of test status.

One task per session. The dependency chain is deliberately narrow so that data model and rendering errors surface before an interface hides them.

## Performance, proposed on 2026-09-09 and not yet accepted

This section is a plan, not a schedule. It was written on 2026-09-09 from `Markdown/32_Performance_Architecture_Investigation.md` and `Markdown/33_Hardware_Optimization_and_Future_Architecture_Research.md`, both of which are research and neither of which authorises anything, against the measurement that made them necessary: `verification/T-06_declared_fixture.md`, where the declared ten-layer fixture costs 264.17 ms a frame at the median of the tenth loop against the 41.7 ms a 24 fps clock allows. That gap is D-47 in document 14 and D-47 is OPEN; nothing below closes it. Every entry here is PROPOSED, and the owner accepts or cuts each one by name. Where the two research documents disagree, document 33 is the corrected reading: the tenth-loop median is 264.17 ms, not 267.17; the sRGB encode in `to_srgb8_straight` is on the preview path as well as the export path; After Effects' SmartFX does declare regions; Resolve reuses upstream nodes. Where they agree, they agree on the thing that matters most, which is that nobody has measured where the frame goes, so the first unit measures and builds nothing.

Rules that bind every entry. **No expected value in `Fixtures/` or document 25 changes**, which is document 12's rule and needs no restating except that performance work is where the temptation is strongest. **No estimate from either research document is quoted as a result**; the only figures a P-entry reports are ones its own artifact measured, on the recorded machine, build and commit. **Savings are not added or multiplied**: document 33's arithmetic on this is right, and an item that saves half of a stage saves half of that stage, nothing more, until the timer says otherwise. **One unit at a time**, per document 04 line 45, and the order below is a dependency order rather than a promise. **ADR-006 stays with the owner**: its trigger has fired on a recorded measurement, which makes the record open to a decision, not reopened by an agent, and P-07 exists to put one number in front of that decision rather than to take it. **ADR-011, ADR-015 and ADR-017 hold as written** unless an entry says which one it would void and the owner amends it first.

Where this sits against B-12 and the interface redesign document 05 lines 73 to 75 describe. B-12 comes first and is the owner's. P-01 and P-02 are cheap, change no pixels and touch no interface, and can run in the same window as the redesign; P-04 changes how the page asks for frames and should land before the redesign replaces the page, so that the new page inherits the request model rather than rediscovers it. P-01 and P-04 between them are also the observed baseline document 05 line 69 says the efficiency targets wait on. Everything from P-03 on is renderer work and, by document 04's rule, does not run at the same time as the redesign.

P-01 / Where the frame goes. PROPOSED. Depends on B-12 only in courtesy: it changes no picture and can run beside it. Document 32's SP-P1 and document 33's PERF-R01 asked for the same instrument, and this is it: a per-stage timer through one frame of each fixture, the reference shot and `verification/T-06_declared_fixture.json`, at draft and at full, in a release build, on the recorded machine. The stages are the ones the code already has, named in the order they run: the wait for the viewer lock in `serve` (`app/src/main.rs` line 234); building the plan; for each layer, opening and reading the file, PNG decode, the byte-to-f32 conversion and the transfer function (`src/color.rs` line 18), the cache lookup and its copy (`src/cache.rs` line 163), the mask, each effect in the stack; then the tile loop (`src/render.rs` line 274), assembling the frame (line 278), `to_srgb8_straight` (`app/src/main.rs` line 351), and handing the bytes to the page. Separate three cache states and say which each row is: application cache cold, application cache cold with the operating system's file cache warm, and everything warm; document 33 is right that the T-06 "cold" loop never established the first of these. Scope is timers and a table, and the timers should be `Instant::now()` around stages reported through the trace mode ADR-012 already gives the build, not a profiling framework. **Not in scope: any optimisation, however obvious it looks while the timers go in.** Artifact: `verification/P-01_frame_trace.md`, one table per fixture per quality, p50 and p95 per row, whose rows sum to the measured frame time with the residual stated, and a line for each cache state. Exit: the "everything else" row document 32 section 1.2 could not account for, about half the frame, has become named rows, and the residual is small enough to say so. The exit condition is met: the residual is 3.7% to 8.4% of a frame, so the half-frame document 32 could not name is named. What it found, in the order it ranks the work, is not the order either research document proposed. **The transfer function and premultiply is first in every cold row** (30.7% to 50.7%), which promotes P-03(c) from third item to first. **Copying the cel in and out of the cache is second** (11.1% to 13.4% admitting it cold, 13.4% to 55.6% looking it up warm), which is P-03(a). **The tile loop is 1.3% to 7.8% of every frame measured**, which demotes P-05 to near-worthless and settles the SIMD question below. **The effect stack is 23.2% to 65.2% of every declared-fixture row**, which no research document ranked and which P-09 below now carries. **The encode is 11.6% to 63.2%**, which P-03(c) deliberately excluded and which P-10 below now revisits. P-02 / Prefix reuse, counted on paper. PROPOSED. Depends on nothing and writes no code under `src/`. Document 32 section 6.2 argues that a run of frames whose lower layers hold the same drawings, transforms, effects and mattes composites those layers identically every frame, and that a deterministic renderer can cache that partial composite on a hash of its inputs rather than hope. Document 33 agrees it is promising if the stable prefix dominates cost, and neither document knows whether it does on real artwork. This unit counts, the way `verification/derive_d37_reuse.py` counted decode reuse without running the compositor: read the exposure sheets of both fixtures and report how many frames of each have a stable bottom prefix, how deep it goes, and what fraction of layer samples it would eliminate. Artifact: `verification/P-02_prefix_reuse.md` and the script beside it. Exit: a number. If it is small, P-08 dies here and this section says so; if it is large, P-08 becomes worth proposing to the owner as a G2 record. **DONE**, and the artifact is `verification/P-02_prefix_reuse.md` with `verification/derive_p02_prefix.py` beside it. The exit condition asked for a number and the number is this: **the stable prefix between consecutive frames is one layer deep, on all 239 transitions of both fixtures, with no exceptions.** The layer that moves on ones sits second from the bottom of both stacks, so the run of frames document 32 section 6.2 describes does not occur. A cache keyed on the prefix's inputs rather than on adjacency does find reuse, because the exposures are periodic with periods of 24, 24 and 60 frames and the shot comes round again, but reaching it costs memory this project has twice declined to assume: within the 1 GiB D-40 sets, the cache removes 24.9% of the reference shot's layer composites and 10.0% of the declared fixture's, and in both cases the layers it removes are the same one, the static background, whose decoded pixels `src/cache.rs` already holds. 45.5% on the declared fixture needs 40.45 GiB. What this does not say is that prefix caching is a bad idea in general: it says these two fixtures put the fastest-moving layer at the bottom, and a shot drawn the other way round would rank differently. The script takes a project file and an exposure sheet, so a fixture like that could be counted the day one exists.

P-03 / Tier 0: the bit-exact removals. PROPOSED. Depends on P-01, which supplies the baseline and the order. ## Definition of ready and done

Ready: requirement, input fixture, expected behavior, prerequisites and dependency status are understood, and the expected values already exist independently of any implementation.

Done: behavior works, relevant fixtures pass, the verification artifact exists and the owner has reviewed it, documentation matches actual behavior, and the report states what was not run. A partial interface is not completion.

For the first coding session use B-01. Do not attempt several backlog items in one session because they look small.
