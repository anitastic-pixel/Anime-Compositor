# Implementation backlog and task briefs

Version 0.3 | 2026-09-04 | Accepted for baseline

## Backlog rules

Each entry states its own progress; at version 0.3 every task began NOT STARTED. Sequence reflects dependencies, not calendar. Every task attaches a verification artifact per document 12 before it closes. A task without an artifact the owner has reviewed is not done, regardless of test status.

One task per session. The dependency chain is deliberately narrow so that data model and rendering errors surface before an interface hides them.

## Performance, proposed on 2026-09-09, accepted or cut entry by entry

This section is a plan, not a schedule. It was written on 2026-09-09 from `Markdown/32_Performance_Architecture_Investigation.md` and `Markdown/33_Hardware_Optimization_and_Future_Architecture_Research.md`, both of which are research and neither of which authorises anything, against the measurement that made them necessary: `verification/T-06_declared_fixture.md`, where the declared ten-layer fixture costs 264.17 ms a frame at the median of the tenth loop against the 41.7 ms a 24 fps clock allows. That gap is D-47 in document 14, accepted on 2026-09-12 as a stated limit of the envelope; nothing below closes it. Every entry here was PROPOSED, and the owner accepted or cut each one by name; each entry says which. Where the two research documents disagree, document 33 is the corrected reading: the tenth-loop median is 264.17 ms, not 267.17; the sRGB encode in `to_srgb8_straight` is on the preview path as well as the export path; After Effects' SmartFX does declare regions; Resolve reuses upstream nodes. Where they agree, they agree on the thing that matters most, which is that nobody has measured where the frame goes, so the first unit measures and builds nothing.

Rules that bind every entry. **No expected value in `Fixtures/` or document 25 changes**, which is document 12's rule and needs no restating except that performance work is where the temptation is strongest. **No estimate from either research document is quoted as a result**; the only figures a P-entry reports are ones its own artifact measured, on the recorded machine, build and commit. **Savings are not added or multiplied**: document 33's arithmetic on this is right, and an item that saves half of a stage saves half of that stage, nothing more, until the timer says otherwise. **One unit at a time**, per document 04 line 45, and the order below is a dependency order rather than a promise. **ADR-006 stays with the owner**: its trigger has fired on a recorded measurement, which makes the record open to a decision, not reopened by an agent, and P-07 exists to put one number in front of that decision rather than to take it. **ADR-011, ADR-015 and ADR-017 hold as written** unless an entry says which one it would void and the owner amends it first.

Where this sits against B-12 and the interface redesign document 05 lines 73 to 75 describe. B-12 comes first and is the owner's. P-01 and P-02 are cheap, change no pixels and touch no interface, and can run in the same window as the redesign; P-04 changes how the page asks for frames and should land before the redesign replaces the page, so that the new page inherits the request model rather than rediscovers it. P-01 and P-04 between them are also the observed baseline document 05 line 69 says the efficiency targets wait on. B-44 / The GPU draws the viewer's picture: compositing only, behind a switch / **accepted with D-100 (a) on 2026-09-25 and BUILT the same day; it awaits the owner's playtest.** What was built and measured is in `verification/B-44_gpu_preview.md`; the playtest is `verification/B-44_gpu_playtest.md`. **The finding that changes the order of work:** with no effects to run, the GPU is no faster than the CPU. At Draft it is slower, at Full about even, because most of its time goes on sending new drawings to the card. The time to win is in the effects, which is what the units after this one do. It depended on B-43 being tested and pushed first, so the GPU work started from a clean, committed build.
- **What it builds.** A GPU version of `render::render` for the preview only. It does `render_tile`'s work over the frame: each layer's transform, bilinear sampling with transparent black outside the drawing, opacity, the alpha matte, and document 21's four blend modes. It then does `to_srgb8_straight`'s encode on the card, so only the finished eight-bit picture comes back.
- **Design rules from P-07:**
  - The inverse transform is worked on the CPU in f64 and handed over. The GPU never inverts one.
  - Drawings are uploaded once and kept on the card between frames. The card holds its own reference to each drawing, so a drawing still in use is never freed and replaced by a different one.
  - The card's store has a budget with least-recently-used eviction, like D-40's.
  - The tool is wgpu. Nothing is copied from `spikes/p07_gpu`, which stays quarantined.
- **What it hands back to the CPU:**
  - Effects still run on the CPU exactly as now (ADR-017, D-99). Their finished drawing is what gets uploaded.
  - Any frame containing an adjustment layer (D-66) is drawn wholly by the CPU, because an adjustment layer runs effects on the frame drawn so far.
  - Every fallback is written in the frame log. None is silent.
- **The switch.** Preview gets a CPU / GPU choice. It starts on CPU and stays there until the owner passes the playtest. If no suitable card is found, the switch says so and stays on CPU.
- **Unchanged:** export, every fixture, and Full-quality checking, which all stay on the CPU byte for byte.
- **The evidence, written before the GPU code** so the check is fixed first:
  - `tests/b44_gpu_preview.rs` renders the four H-01 frames P-07 measured (0, 14, 100 and 239), P-07's hard-rotation case, and the reference shot and the ten-layer fixture at Draft and at Full, on both CPU and GPU.

  - A second table gives GPU and CPU frame times side by side, with machine, build, card, driver and backend.
  - For the worst frame there is an old / new / difference picture, the difference amplified.
  - One row checks that each fallback case (a frame with an adjustment layer) is logged, and that its picture is byte-identical to the CPU's.
  - On a machine with no usable card, the table says the check was not run. It never passes a check it did not run.

## Reuse from open source, proposed on 2026-09-22, accepted or cut entry by entry

This section is a plan, not a schedule. It was written on 2026-09-22 from `research/2026-09-22_github_reuse_survey.md`, which is research and authorises nothing. The owner asked whether anything already built could be branched from or taken in. The answer for whole applications is no, and it is recorded in document 30; the answer for parts is the four entries below, each of which stays PROPOSED until the owner accepts it by name in document 14.

Rules that bind every entry. **A port is a dependency, so document 10 applies in full**: the origin URL, the exact commit, the licence text and the copyright notice are recorded before any code is written, and the notice ships with the build. **Nothing here is copied from a GPL, LGPL or MPL project**; Friction, Natron, Synfig, Glaxnimate and Blender are reference only, which is what document 30 now says. **The fixtures come first**, as they did for B-24a and B-25a: a ported algorithm is specified, drawn and fixtured against our own expected values, never accepted because the original passes its own tests. A port that cannot be explained in a proposal is not ready to be built.

R-01 / The exposure timesheet read (XDTS). PROPOSED, and the highest value of the four for anime work, because it is the one thing on the list that removes work the owner cannot do at all today. CELSYS publishes the format as a public specification PDF, so the parser is written from the specification rather than from anyone's code. Three permissive readers exist to check ours against: OpenToonz `toonz/xdtsio.cpp` and `opentoonz/xdts_viewer`, both BSD-3, and `lunafuse/vdts-editor`, MIT, which is also the only reader found for the older TDTS. No Rust crate exists. Its fixture would be a timesheet in and an exposure out, and the round trip back. Document 31's roadmap places it at G2b; document 04 has no line for it yet, and adding one is part of the decision. **Taken up on 2026-09-23 as B-28, under D-84 (proposed).**

R-02 / Line smoothing. PROPOSED. OpenToonz `common/trop/tantialias.cpp` is about four hundred lines of BSD-3 and uses the published method that OLM's page says OLM Smoother uses. `loilo-inc/smooth` and its OpenFX port `cr-market/anime-smoother-ofx` are Apache-2.0 and a different method, which makes them a second opinion rather than a second copy. This is document 31's D-06 and its G3a. OLM's own tools are Apache-2.0 but ship as built plugins only, so there is no OLM source to take. **Taken up on 2026-09-25 as B-30, under D-86 (accepted).**

R-03 / The cel colour operations. PROPOSED. `bryful/F-s-PluginsProjects` is MIT and holds about forty effects by a working anime creator; `cr-market/FsPluginsOFX` ports eight of them, including main-line repaint, selective colour blur and select colour, in a form separated from the After Effects SDK. This is document 31's D-06, D-07 and D-09. The smallest useful first behaviour is one operation, not the set. **Taken up on 2026-09-25 as B-31, selective colour blur first, under D-87 (accepted).**

R-04 / The blur and glow family. PROPOSED, and last of the four because the existing Gaussian blur already covers part of it. OpenToonz `stdfx` holds directional, radial, rotate, line and motion blur, erode and dilate, glow, bloom and glare, and the RGB and HSV keys, all BSD-3, and its `igs_*` cores depend on nothing but the C++ standard library. This is document 31's D-07, D-08 and D-10. **Line recolour, directional blur, select colour, line width, radial blur, bloom and colour key are taken up on 2026-09-25 as B-35 to B-41, under D-91 to D-97.** **Taken up on 2026-09-25 as B-33, glow first, under D-89 (accepted).**

Not proposed, and why, so that the next reader does not re-derive it. Toon Dilate and distance gradation: no source exists, and OLM's page describes the method well enough that writing it is smaller than searching further. KiraKira and paraffin gradients: nothing was found at all. An OpenFX host: the ASWF headers and its HostSupport library are BSD-3 and would be the reference, but no Rust host exists and the job is large, so it stays where document 31 put it, at G3e behind a plugin the owner actually needs. Lottie: `velato` is a permissive Rust reader worth using as a model, but the format is only worth reading when vector interchange is in scope. A whole-application fork: refused in document 30 on 2026-09-22.

The libraries that would come with later features, none of them proposed here and each named so the search is not repeated: `kurbo` for miter and bevel joins, caps and trim paths, and `i_overlay` for merge paths, when D-78's exclusions are lifted; `harfrust` and `skrifa` for text layers, drawn through our own shape rasteriser so that text and shapes match; `wgpu` if ADR-006's stopwatch fires. Written ourselves rather than taken: gradients, repeaters, the `.cube` lookup table, frame blending and the waveform display, each because the dependency is larger than the code it saves. Avoided: `symphonia`, which is MPL-2.0.

## Definition of ready and done

Ready: requirement, input fixture, expected behavior, prerequisites and dependency status are understood, and the expected values already exist independently of any implementation.

Done: behavior works, relevant fixtures pass, the verification artifact exists and the owner has reviewed it, documentation matches actual behavior, and the report states what was not run. A partial interface is not completion.

For the first coding session use B-01. Do not attempt several backlog items in one session because they look small.
