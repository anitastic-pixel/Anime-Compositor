# Decision, assumption and risk register

Version 0.3 | 2026-09-04 | Accepted for baseline

## Decision procedure

Every decision record contains ID, question, recommendation, evidence basis, owner, status and date. Entries may be ACCEPTED FOR BASELINE, PROVISIONAL or OPEN. Version 0.3 closes the decisions that version 0.2 left open, on the basis of a structured design interview with the owner rather than measurement. Where a decision rests on preference rather than evidence, this document says so explicitly.

Andrew is the product decision owner, the artistic acceptance reviewer and the sole verifier. No technical or legal reviewer is engaged.

## Closed decisions

D-01 / Platform / ACCEPTED. Windows 11 x64 only for G0 through G1. Declared reference machine: Ryzen 9 9900X, 64 GB RAM, RTX 4070 Ti Super 16 GB. Cross-platform support is not claimed, planned or designed for. Platform-specific code stays behind narrow interfaces so that this remains reversible, not because a port is scheduled.

D-02 / Initial scope / ACCEPTED. Complete the 2D milestone before any 2.5D work. Version 0.3 narrows this further: see D-12.

D-03 / Distribution / ACCEPTED. Open source. This decision was taken early and deliberately in order to remove license review as an ongoing cost, since no legal reviewer is available. All dependency choices must remain compatible with it. Revenue is not a project goal.

D-04 / Capacity / PROVISIONAL. Solo development with Claude Code on a subscription, no API spend, owner as sole reviewer. Weekly hours are deliberately not committed. Consequence: document 13 remains gate-driven with no calendar dates, and no estimate in this pack may be converted into a completion date until this is closed.

D-05 / Reference shot / ACCEPTED. The owner draws it. Specification is in document 22: 1920x1080, 24 fps, 240 frames, one static background, three cel layers on 1s, 2s and 3s with a deliberate five-frame hold and a one-frame accent, mixed soft and hard and semi-transparent edges, one deliberately missing frame and one Japanese filename. Rights-cleared by construction.

D-06 / Stack / ACCEPTED, spike-confirmable. Rust core with rayon for tile parallelism, Tauri with an HTML and CSS interface. Rationale in ADR-003 and ADR-004. Selected against the constraint that the owner cannot read code, which favors a compiler that rejects broken programs and a toolchain with no configuration surface for the owner to repair.

D-07 / Color / ACCEPTED. Linear-light premultiplied float32 working space with explicit PNG interpretation, per document 21.

D-08 / Compatibility / ACCEPTED. Native features only. No AE project import, no binary plugin hosting, no expression translation. Not a research topic during G1.

D-09 / G2 geometry / ACCEPTED. Non-intersecting planes with explicit order, when G2 is reached.

D-10 / Expressions / DEFERRED. G2 concern. The likely answer within a Rust core is an embedded sandboxed scripting runtime or a small custom evaluator, but this is not decided and must not influence G1-core design. **Answered on 2026-09-16 by D-59, accepted by the owner the same day:** a small custom evaluator, not an embedded runtime.

D-11 / Name / DEFERRED. TotallyNotAfterEffects is a working title and repository name only. It is a joke, not a product name, and it references a competitor trademark, which makes it unsuitable for distribution. Choose and screen a public name before any public build.

## New decisions in version 0.3

D-12 / G1-core narrowing / ACCEPTED. The fifteen-Must G1 list from version 0.2 is split. G1-core is import, exposure timing, layers and transforms, undo, save and recovery, export, color and alpha handling, and offline operation. Masks and mattes, the effect stack, and the bounded preview cache are parked to G1-rest. Rationale: at the available capacity the version 0.2 list was not deliverable, and document 30 identifies exposure-and-layer-first finishing as the only structural gap against existing free tools. Masks and blur are not gaps.

D-12 amended on 2026-09-06: the park on masks and mattes (B-06 / R-04) and on the effect stack (B-07 / R-05) is LIFTED, both together, by the owner. The owner fired both on being shown what the alternative costs: B-12 / G1 acceptance needs W-01 finished on the reference shot, W-01 needs a matte, a blur and a colour operation, and with the backlog B-01 through B-11 and B-08b complete there is no decision-free work left that reaches G1. What is not lifted: nothing else in G1-rest moves, the narrowing that produced G1-core stands as the reason this project got this far, and B-07 must still address the ADR-011 tile margins that document 15 line 69 names as part of why blur was not in the first milestone. This entry records the decision; the unpark is written into R-04 and R-05 in document 03 in the form R-06b set on 2026-09-05. D-13 / Verification model / ACCEPTED. The owner cannot read code. Human source review is removed from the quality system and replaced by fixture-and-artifact verification, specified in document 12. D-16 / Pack format / ACCEPTED. Word review copies and the checksum manifest are removed. Markdown is the only source and the repository is under git, which supplies the change record this document previously described by hand.

## New decisions in version 0.4

D-17 / sRGB transfer function / PROVISIONAL. Document 21 requires conversion between sRGB and linear light in both directions but never states which transfer function. B-02 implements IEC 61966-2-1: linear segment `c/12.92` below `c <= 0.04045`, and `((c+0.055)/1.055)^2.4` above, with the matching inverse. Evidence basis: this is the transfer function the sRGB standard defines and the one every tool the owner would compare against uses. Status is PROVISIONAL rather than ACCEPTED because it is an agent's reading of an unstated requirement, not an owner decision. Consequence if changed: every expected value in `verification/B-02_fixture_table.md` moves, and document 25's fixtures move with it.

D-18 / 8-bit quantisation rule / PROVISIONAL. Document 21 says "final integer output conversion clamps only at the declared encoding step" but does not state the rounding rule at that step. B-02 clamps to 0..1 and rounds to nearest with ties away from zero, `floor(c * 255 + 0.5)`. Evidence basis: it is the rule the G0 spikes already used, and it makes all 256 8-bit codes survive a decode and re-encode round trip exactly, which is stronger than the "at most one code value" tolerance document 25 allows. Status PROVISIONAL for the same reason as D-17. Both should be folded into document 21 as specification text rather than left as implementation comments.

## Risks

K-01 / High / Scope expansion. Effect catalogs and conveniences displace core reliability. Trigger: anything from the parked list appearing in a build. Mitigation: the admission rule in document 04, the parked list in document 23, and the agent rule forbidding parked work.

K-02 / High / Pixel errors. Alpha and color mismatch damages edges. Trigger: halos, or preview and export disagreeing. Mitigation: independent fixtures, tagged buffers, render trace.

K-03 / High / Data loss. Partial writes or migrations damage projects. Trigger: failed recovery fixture. Mitigation: atomic replacement, autosave, T-07.

K-04 / High / Unverifiable implementation. The owner cannot detect a wrong implementation that passes its fixtures, or a fixture quietly weakened. Trigger: unexplained fixture changes, or reports lacking artifacts. Mitigation: document 12, the fixture read-only rule, mandatory artifacts, mandatory not-run reporting. This risk is inherent and permanently open.

K-05 / High / Capacity. The project is large and the owner is one person without a coding background. Trigger: milestone stalls, growing unfinished subsystems. Mitigation: the D-12 narrowing, one subsystem at a time, willingness to narrow again.

K-06 / Medium / Preview transport ceiling. WebView2 frame delivery may not sustain full-resolution playback, and browser color management may alter displayed pixels. Trigger: SP-05 or SP-06 failing. Mitigation: both are preview-side only and never affect export; the fallback is a native viewer surface inside the web shell.

K-07 / Medium / Unsafe input. Malformed media exhausts resources. Trigger: unbounded parser. Mitigation: size limits and cancellation.

K-08 / Medium / Dependency drift. WebView2 is a system component updated by Microsoft outside the control of this project. Trigger: a Windows update changing viewer behavior. Mitigation: viewer color and transport fixtures run against each release candidate.

D-19 / Four import diagnostic identifiers / PROVISIONAL. Document 28's catalog defines `MEDIA_SEQUENCE_GAP`, `MEDIA_UNSUPPORTED_FORMAT` and `MEDIA_DECODE_FAILED`, which cover most of B-03. Test T-01 also requires behaviour for mismatched dimensions within one sequence, and the reference shot forces two more cases, and document 28 names none of them. B-03 adds `MEDIA_SEQUENCE_DIMENSION_MISMATCH` (WARNING, the sequence is treated as the majority size and the odd drawings are still imported), `MEDIA_SEQUENCE_DUPLICATE_NUMBER` (ERROR, two selected files claim one drawing number, the first in sort order is kept), `MEDIA_SEQUENCE_UNNUMBERED` (ERROR, a selected file has no number in its name and is excluded) and `MEDIA_SEQUENCE_NAME_VARIANT` (INFO, a file carries a clear number under a name the inferred pattern does not generate, and is imported under its own name). Evidence basis: document 28 requires stable machine IDs and forbids library error strings as user-facing identifiers, so silence was not an option and reusing an unrelated identifier would have been a silent reinterpretation of the catalog. Status PROVISIONAL because the names and severities are an agent's proposal, not the owner's decision. Consequence if changed: the identifiers in `verification/B-03_import_table.md` change, and document 28's catalog gains four entries.

D-20 / Frame numbers come from the file list, not the pattern / PROVISIONAL. Document 19 line 17 requires a sequence asset to store a numeric pattern and a frame-number-to-file map "so missing numbers remain missing rather than being silently compacted", but does not say which of the two decides membership. B-03 makes the map authoritative and the pattern descriptive: a frame number is the last run of ASCII digits in a file's stem, and a file whose name the pattern does not generate is still imported under its own name. Evidence basis: the reference shot requires it. Drawing 13 of layer 2 is `layer2_桜_013.png`, which `layer2_%03d.png` does not generate; a pattern-driven importer reports a false gap and drops a drawing the owner can see in their own folder. Consequence if changed: layer 2 would report a gap it does not have.

D-21 / Three command diagnostic identifiers / PROVISIONAL. Document 26 requires that a command validate intent and that "a rejected command does not change document revision, dirty state, undo stack or caches", and document 28 forbids surfacing a library error string as a user-facing identifier, but document 28's catalog names no identifier for a command that fails validation. B-05 adds `COMMAND_TARGET_MISSING` (ERROR, the command named a composition, layer or keyframe that is not there), `COMMAND_INVALID_VALUE` (ERROR, the command carried a value the model cannot hold: the wrong value kind for the property, a non-finite number, or an index outside the layer stack) and `COMMAND_LAYER_LOCKED` (ERROR, the command would have changed a locked layer). B-05 also raises `MATTE_REFERENCE_MISSING` and `MATTE_CYCLE`, which document 28 does list; it raises them as ERROR from the command that would create the bad reference, where the catalog's WARNING wording describes one found while loading a project. Evidence basis: rejection has to be reportable to be verifiable, and the rows in `verification/B-05_model_table.md` that prove a rejected command changed nothing are keyed on these identifiers. Status PROVISIONAL because the names and severities are an agent's proposal, not the owner's decision. Consequence if changed: those rows change and document 28's catalog gains three entries.

D-22 / Scale is stored as a unit factor, not as a percentage / PROVISIONAL. Document 21 writes the transform chain as `T(position) * R(rotation) * S(scale/100) * T(-anchor)`, which reads the stored scale as a percentage where 100 means unchanged. Document 19 line 25 says scale "is percentage-like in UI but serialized as explicit numeric pairs", and B-05's shipped model already defaults a new layer's scale to `(1, 1)`. B-05a resolves the two in favour of the unit factor: the model and the renderer take 1.0 as identity, and the divide by 100 belongs at the UI boundary, next to the degree sign and the percent sign. Evidence basis: under the other reading every layer created by B-05 renders as a one-percent speck, and the default the owner would see on a new layer would have to be the number 100 in a field document 19 describes as a numeric pair. Status PROVISIONAL because document 21's wording still says `/100` and only the owner can amend it. Consequence if changed: document 21's transform formula and `Affine::from_transform` in `src/render.rs` change together, and every scale value in every saved project changes by a factor of a hundred. B-09 adds evidence the earlier reasoning did not have: every project fixture in `Fixtures/projects/`, all written by hand before any code existed, writes `"scale": { "base": [100, 100] }` for a layer at natural size. The stored form is therefore settled - the file says 100 - and the only live question is where the divide happens. `src/persist.rs` does it at the file boundary and nowhere else, so the model, the renderer and document 21's `S(scale/100)` are all satisfied at once and the fixtures round-trip byte for byte.

D-23 / Trace images are written display-encoded, not in the working space / PROVISIONAL. ADR-012's consequences say "Trace images are written in the working space and tagged with their alpha mode and color space", and the same ADR's rationale says the point of trace mode is that "the owner can see which layer went wrong". Those two pull against each other: the working space is linear light with premultiplied alpha, and a linear-light PNG opened in any ordinary viewer looks wrong, which is the one thing a diagnostic image must not do. B-05b writes trace PNGs through exactly the conversion export uses — unpremultiply in linear light, sRGB transfer function, quantise to 8 bits, straight alpha — and keeps the tagging requirement in full: every file carries `ColorSpace`, `AlphaMode` and a `WorkingSpace` chunk naming what it was converted from, and the manifest repeats it. Evidence basis: an untagged or unviewable trace image fails the ADR's own justification. Status PROVISIONAL because ADR-012's wording still says working space and only the owner can amend an ADR. Consequence if changed: trace images become 32-bit float or 16-bit linear PNGs the owner cannot judge by eye, and the facility would need a second, viewable output beside them.

D-24 / A structurally valid record of a parked feature is reported as `PROJECT_FEATURE_UNSUPPORTED` / PROVISIONAL. Document 28 names `EFFECT_UNSUPPORTED` for an effect this build does not have, and nothing at all for a record of a feature that is not an effect. Masks are the case that exists today: document 23 parks them with R-04, `Schemas/project-v0.schema.json` carries a `mask` field, and B-09 must therefore decide what happens when a valid project arrives with one. Silence is not available - CLAUDE.md and document 28 both forbid a silent fidelity fallback, and rendering the layer as though the mask were not there is exactly that. B-09 raises a WARNING under the proposed identifier `PROJECT_FEATURE_UNSUPPORTED`, preserves the record untouched through save, and excludes it from rendering. Evidence basis: the same reasoning document 28 already applies to `EFFECT_UNSUPPORTED`, applied to the only other parked feature the schema can express. Status PROVISIONAL because only the owner adds an identifier to document 28; `tests/b09_persistence.rs` asserts that this identifier is *not* in the catalogue, so the assertion fails and points at itself on the day it is added. Consequence if changed: the identifier is renamed in `src/diagnostics.rs` and in one test row, or masks become an ERROR that refuses the project, which would make a G1 build unable to open a project a G1-rest build wrote.

D-25 / Repeated frame-level warnings are logged in full three times, then summarised once with a count and frame ranges / PROVISIONAL. Document 28 requires that "repeated frame-level warnings should be rate-limited while retaining counts/ranges" and gives neither a number nor a shape. Two things had to be chosen to write any implementation at all: how many occurrences are logged before suppression begins, and whether the summary replaces them or follows them. B-04b logs the first three in full, suppresses the rest, and appends one summary per group carrying the total, the frame ranges, and the identifier, severity and remediation of the first occurrence. Grouping is by identifier and a caller-supplied subject, never by message text, because a frame-level message names its own frame and so no two are ever equal - grouping on the message would suppress nothing. Evidence basis: the reference shot raises one warning on each of twenty frames, and the rate-limited log of that walk is `verification/B-04b_frame_log_table.md`. Status PROVISIONAL because the number three and the log-then-summarise shape are the loop's choice, not document 28's. Consequence if changed: `FrameLog::new` already takes the limit as an argument, so a different number is a caller's decision and no code changes; ruling that the summary should replace the individual records rather than follow them changes `finish` and the expected strings of about six rows in one test.

D-26 / A render asked for a frame the composition does not have is refused as `COMMAND_INVALID_VALUE` / PROVISIONAL. Document 20 step 1 requires the composition frame to be validated before anything else is evaluated, and document 28's catalog names no identifier for failing that validation: its command identifiers describe a command that edits the document, and a render request edits nothing. B-08a reuses `COMMAND_INVALID_VALUE`, the identifier D-21 introduced for a command carrying a value the model cannot hold, on the reasoning that a frame number outside the composition's range is exactly that kind of value. It refuses rather than clamping: rendering the nearest frame the composition does have would answer a question nobody asked and hide the mistake. Evidence basis: `verification/B-08a_compose_table.md` refuses frame 240 and frame -1 of a 240-frame composition that starts at 0, and renders frame 239. Status PROVISIONAL because reusing a command identifier for a render request is an agent's reading, not the owner's, and document 28 may prefer a distinct name such as `RENDER_FRAME_OUT_OF_RANGE`. Consequence if changed: one identifier in `src/compose.rs`, one entry in `src/diagnostics.rs` and two rows in `verification/B-08a_compose_table.md`.

D-29 / A negative composition frame keeps its minus sign in front of the padded digits in an exported file name / PROVISIONAL. D-32 / Playback that cannot keep up drops frames and holds real time / CLOSED by the owner on 2026-09-05. SP-05 measured 24.9 fps at full resolution against a 24 fps target, about four percent of margin, so a viewer that plays a shot has to be told what to sacrifice when it falls behind. The two answers are not interchangeable: dropping frames keeps the timing true and may not show every drawing, while showing every drawing runs the shot slow and makes the timing a lie. The owner chose to hold real time, on the reasoning that judging timing and spacing is what playback is for, and inspecting an individual drawing is what frame stepping is for. Consequence: B-08's playback clock is wall-clock driven rather than frame-driven, it skips the frames it cannot deliver in time, and the viewer must report how many it skipped rather than hiding it - a silently dropped frame is a fidelity fallback and document 28 forbids those. Evidence basis: SP-05's measurement in `spikes/B-01_G0_spike_report.md`.

D-33 / The preview defaults to draft resolution with a visible indicator / CLOSED by the owner on 2026-09-05. SP-05 measured 145 fps at draft against 24.9 at full, so the default decides whether scrubbing is comfortable or marginal. R-06a already requires "a visible indication when preview quality differs from final export", which makes the draft default safe: the owner is never left believing they are looking at final pixels. Full resolution remains selectable, and export never passes through the display path at all, so nothing here can reach a delivered frame. Consequence: B-08 carries a resolution selection with draft as its initial value, an always-visible indicator of which is active, and a preview-versus-export pixel comparison at full resolution as part of its exit artifact. Evidence basis: SP-05, and R-06a's own wording. Qualified but not reopened on 2026-09-05 by `verification/B-08_preview_latency.md`, which measured the production preview path rather than a spike and found draft only slightly faster than full, because three quarters of a frame's cost is decoding cels and a drawing is decoded at its own size whatever the preview extent. Draft remains the faster of the two and remains the default; what the measurement changes is the expectation of what the default buys, and it is what fired the cache's revisit trigger. See D-37.

D-34 / The copyright holder named in `LICENSE-MIT` is `anitastic-pixel` / CLOSED on 2026-09-05, by the owner, who delegated the call to the agent's recommendation. D-31 chose the licence; it did not choose whose name sits on the notice. The answer is that the notice keeps what it already said - `Copyright (c) 2026 anitastic-pixel` - and the placeholder becomes the decision. Three reasons. It is the only identity this project is published under: it owns the repository and authors every commit in it, so the notice matches a record a reader can check rather than a name that appears nowhere else. A copyright notice is valid under a consistently used name and does not require a legal one. And a legal name in a public file is the one edit in this repository that publishes something about a person rather than about a program, which makes it the wrong kind of thing for an agent to write on the owner's behalf even when asked to decide - the cost of guessing wrong is not a broken build. The owner replaces the line the moment they want their legal name on it, and nothing else moves, because no check asserts the name: a name is not a thing a fixture can derive. Consequence if changed: one line in `LICENSE-MIT`. Evidence basis: `LICENSE-MIT`, which this decision leaves byte for byte as it was.

D-35 / The frame shown at rest is the work area's first frame / PROVISIONAL, taken by the agent on 2026-09-05 while building B-08's playback clock. D-57 / Parenting: a layer may ride on another layer's transform / ACCEPTED on 2026-09-15 by the owner ("I accept it"), written by the agent under D-56 with its fixtures first. **What is already there:** every layer is placed on its own, by document 21's transform. **What is not there:** any way to say that a mouth cel moves with its head cel, other than keying both the same. **The field.** A layer gains an optional `parent`: the ID of another layer in the same composition. Absent or null means no parent, and the file carries the field only when it is set, so no existing project changes. **The math.** The parent's whole transform is applied after the child's own, `M_world(child) = M_world(parent) * M(child)`, up the chain to a layer with no parent. A child's position is therefore a point in its parent's layer space. Position, rotation, scale and anchor reach the child through that product; **opacity, effects, masks, mattes, blend mode and exposures do not**, which is After Effects' rule. A parent is read at the same frame as its child, whether or not that frame is inside the parent's in and out points, and whether or not the parent is switched on or drawn at all, so a hidden layer can be a handle that moves others. **Keeping place.** Setting or clearing a parent keeps the child where it is on screen at the playhead, as After Effects does by default: the new position is the old one carried back through the parent's chain, the new rotation is the old one less the chain's rotations, and the new scale is the old one divided by the chain's scales, applied to the base value and to every keyframe. This is exact when every layer in the chain has equal x and y scale, or when nothing involved is rotated. Otherwise the exact answer is a slant no transform here can hold; the anchor still lands exactly where it was, the rest of the layer can shift, and the window says so rather than hiding it. A parent whose scale is zero at the playhead cannot be undone, so setting it is refused. **What would break a reference.** A chain that loops back on itself is refused as a command and diagnosed as `PARENT_CYCLE` on load, exactly as a matte loop is. A parent ID that names no layer is kept in the file and reported as `PARENT_REFERENCE_MISSING`, and the layer is drawn as if it had no parent. Deleting a parent is **the one place parenting does not copy mattes**: a deleted matte leaves its reference behind, but a child left pointing at a deleted parent would jump, so deleting a parent lets go of its children in place, in the same undo. Duplicating, splitting, copying and pasting carry a parent the way they already carry a matte: to the copy if the parent was copied too, to the same layer if it is in this composition, and let go otherwise. **The fixture came before the code.** FX-PARENT-001 to 008 in document 25, generated by `tools/parent_reference.py`, which walks a point through the four steps of document 21 one at a time and never builds a matrix, while the build multiplies matrices. `Fixtures/projects/parenting_project.json` is a three-layer chain with an animated rotation and a fourth layer whose parent is missing. Documents 07, 19, 20, 21, 25, 26 and 28 and the schema are amended, each marked proposed. Consequence if declined, or changed: the fixtures are rewritten before any code, which is what they are for. A composition gains an optional `camera` with three animatable properties: `position`, a point in composition pixels; `depth`, its own place on the same axis as a layer's; and `zoom`, a length in pixels. Both are written only when set, so no existing project changes. **A composition with no `camera` field is not a composition with no camera.** It has the default one: at the centre of the frame, `zoom` in front of the depth-0 plane, with `zoom` equal to `width * 50 / 36` - a 50 mm lens on a 36 mm film back, which is After Effects' own default, so for 1920 by 1080 that is position (960, 540) with depth and zoom 2666.6666666666665. A layer therefore starts working in depth the moment it is given one, without anybody adding a camera first. **The projection.** Document 21 puts a layer's pixels in composition space and stops. The camera carries them to the screen in two lines: `s = zoom / (world_depth(layer) - camera_depth)`, and `screen = centre + (p_comp - camera_position) * s`, with all three camera numbers read at the frame being drawn. `s` is how big the plane is drawn: 1 on the plane the camera draws at true size, 1/2 on one twice as far, 2 on one half as far, which is the convention D-56 accepted. With the default camera a layer at depth 0 has `s = 1` and lands exactly where document 21 puts it. **The projection is affine, and that is the point of choosing it.** A uniform scale about a point and a shift compose into the single matrix document 21 step 4 already samples through, so a far plane is minified by the bilinear filter G1 already has, in one resampling rather than two. Document 21 line 111 reserved camera projection as a separate contract; this is that contract, and it changes step 4 and the draw order and nothing else. **Identity is exact, not nearly exact.** With the default camera and a layer at depth 0 the two lines are the identity in arithmetic and not in floating point: `960 + (x - 960) * 1.0` is not bitwise `x`. **A build must leave out a projection that is the identity rather than apply one**, so that every fixture written before this entry reproduces exactly instead of within a tolerance. This was found by running the reference generator, not by arguing about it, and FX-CAM-001 is the case that holds it. **Depth is measured from the plane a layer rides on.** A parented layer's depth adds to its parent's, up the chain, exactly as its position is a point in its parent's space, so a mouth cel parented to a head plane is on the head's plane by default and its own `depth` is how far it stands in front of it. D-57 says a parent carries anchor, position, scale and rotation and nothing else; `depth` is a field D-57 never spoke about, and this entry says it is carried, because the alternative leaves every cel parented to a plane floating at depth 0 in front of the plane it belongs to. **Keeping place extends to it**: setting or clearing a parent subtracts or adds the parent's world depth so the layer stays on the plane it was on, and unlike D-57's scale and rotation conversion this one is a subtraction and is always exact. **What is drawn first.** Planes are drawn far to near, and layers at equal depth keep the order the composition gives them. **This overrides the layer stack whenever two layers are at different depths**, which is the one consequence of this entry a person meets without asking for it: bringing a layer to the front of the stack does not bring it in front of something nearer. `layer_order` stays the authority for the list, for ties, and for everything a person drags. This is what W-04 means by occlusion following documented rules. **A matte is a plane too.** Both a layer and its matte are projected at their own depths before the matte's alpha is sampled, so a matte on another plane slides against the layer it shapes as the camera moves. That is correct and it looks like a defect, so it is written down: the window should offer to put a matte on its layer's plane, and this contract does not force it. **What would break a picture.** A layer at or behind the camera's own depth has no size, because `world_depth - camera_depth` is zero or negative: the layer is not drawn, its record is untouched, and `CAMERA_PLANE_BEHIND` says so, which is the shape document 28 already gives `MEDIA_MISSING`. A `zoom` at or below zero is refused as a command and diagnosed as `PROJECT_SCHEMA_INVALID` on load with the camera's record preserved; it is not clamped into a working value. **No shutter**, per D-56: the camera is read once at the frame's own time while a cel holds on its exposure, and motion blur stays where document 21 line 111 put it. **What this takes from After Effects, and what it refuses.** The arithmetic above is already theirs: an After Effects camera scales a plane by its zoom over the distance from the camera to it, and stores that zoom in pixels, which is the first line of this entry. Three things are taken deliberately. The **default lens** is theirs - they name a camera by the focal length of a lens on a 36 mm film back and default to 50 mm, so this entry's default zoom is `width * 50 / 36` rather than the `width` first proposed, and a depth copied out of an After Effects project parallaxes here by the amount it does there (FX-CAM-011). **Depth is animatable** because they keyframe Z constantly and a plane that pushes in is an ordinary shot, not an advanced one (FX-CAM-010). And the window shows the zoom **in millimetres** while the file stores pixels, which is D-22's rule about where a unit is converted, applied to a second number. What is refused is the thing they are named for: **a camera is not a layer here.** In After Effects it is, which buys several cameras in one composition, a camera with in and out points, and a camera parented to a null object - the standard rig. Taking that means a layer kind with no drawing, a parent contract that accepts a camera, and a rule for which camera is live on which frame, and it buys a shot with one camera in it nothing at all. One camera per composition is the multiplane rig this project is for. The cost is named rather than hidden, and a camera layer is a later contract if a playtest asks for one. The other refusal is quieter and worth stating because it is the most confusing thing in their renderer: After Effects applies its camera only to layers whose 3D switch is on, and a 2D layer in the middle of the stack cuts the depth-sorted group in two. Here every layer has a depth and it defaults to 0, so there is no switch to forget, at the price that a layer cannot opt out of the camera to stay pinned in front - which is the one thing the switch is genuinely good for, and is listed below as undecided. **The fixture came before the code.** FX-CAM-001 to 011 in document 25, generated by `tools/camera_reference.py`, which reuses `tools/parent_reference.py` to walk a point through document 21's four steps and then does the two lines above by hand, never building a matrix, while the build multiplies them. `Fixtures/projects/camera_project.json` is FX-CAM-003's three planes and its keyed camera, with a layer order deliberately unlike the draw order. The number the entry exists for is FX-CAM-003's: over 400 pixels of camera travel the near plane moves 400 pixels, the middle 300 and the far 200. FX-CAM-010 is the case the After Effects answer added, where an animated depth changes which plane is in front between one frame and the next. Documents 07, 08, 19, 20, 21, 24, 25 and 28 and the schema are amended, each marked proposed. Document 26 is not: a camera edit is an ordinary command with an ordinary inverse and raises nothing its contract does not already cover. Consequence if accepted: B-13c builds this, W-04 can be walked, and R-12 is fully specified. Consequence if declined, or changed: the fixtures are rewritten before any code exists to argue with, which is what they are for. **Not decided here:** a camera that tilts or turns, which D-56 excluded and which needs a real perspective transform rather than an affine one; a camera as a layer, with the several cameras, in and out points and null-object rig that come with it; whether a layer can opt out of the camera to stay pinned in front of everything, which is what After Effects' 2D switch is good for and which no fixture here needs yet; intersecting planes and depth of field, which document 21 line 111 keeps out; and whether the window puts a matte on its layer's plane by default, which is B-13c's to propose.

D-59 / Expressions: a small language of our own, spelled like After Effects' / ACCEPTED on 2026-09-16 by the owner ("accept d-59"), written by the agent as B-14a with its fixtures first. It answers D-10. **What is already there:** every property is a base and keys (document 20), a composition has a camera (D-58), and a layer is named by an ID that survives a rename. **What is not there:** any way to say "this turns at 90 degrees a second", "this shakes", "this follows that one a quarter of a second late" or "this repeats its keys" without keying every frame by hand, which is R-13. **The choice.** D-10 left two answers open: embed a sandboxed scripting runtime, or write a small evaluator. **This entry chooses the small evaluator**, a language document 09 specifies in full and this project reads and evaluates itself, whose words are After Effects' where After Effects has one - `time`, `value`, `wiggle`, `loopOut`, `valueAtTime`, `posterizeTime`, `linear`, `ease`, `clamp`, `random`, `seedRandom`, `Math`, `thisComp.layer(...)` - so the expressions an animator types most are typed the same way here. **Why not a runtime.** Three of R-13's requirements are hard for a borrowed interpreter and free for an owned one. Seeded randomness must be the same on every machine and every build, so the noise behind `wiggle` is written out to the operation in document 09 and a second implementation reproduces it to the last bit; a runtime brings its own random numbers. Runaway work must stop the same way every time, so evaluation is counted in steps rather than timed, and a language with no loops and no functions has only two ways to run long - a long text and properties reading one another - each with a counted wall. And the sandbox has no door to close, because the language has no word for a file, a network, a process, `eval` or `require`: FX-EXPR-012 is eight attempts, all refused when the text is read. A runtime would also be the largest dependency this project has taken, with a licence and a security record for document 10 to review. **What it costs, named rather than hidden.** It is not JavaScript, and After Effects' language is. An expression copied from a tutorial works here if it uses only the words above and fails with `EXPRESSION_SYNTAX` otherwise, which is visible and never a wrong picture. **There is no `if`, no comparison and no loop in this first version** - many After Effects expressions use `if` - and adding them later is a specification change with fixtures, not a rewrite. **The fields.** A property may carry `"expression": {"text", "enabled"}`, written only when present, on a layer's anchor, position, scale, rotation, opacity and depth and on the camera's position, depth and zoom. A switched-off expression is kept byte for byte and ignored. No existing project changes. **Units** are the file's, except that **opacity is 0 to 100 inside an expression**, because that is what the window shows and what an After Effects user types. Running the reference found a mistake here before any build could make it: the first draft gave an expression reading another layer's opacity 0 to 100 if that opacity had no working expression and 0 to 1 if it had one. FX-EXPR-016 now pins both. **References are by ID**, so a rename never breaks one, where After Effects names a layer by its name or its index. **Failure.** A property whose expression fails is drawn at its keyed value with the identifier shown on that property, a property reading it fails the same way, and **an export whose range meets a failing enabled expression is refused** until it is corrected or switched off, which is document 09's G2 acceptance rule kept. Three identifiers join document 28 beside the two it already had: `EXPRESSION_SYNTAX`, `EXPRESSION_TYPE` and `EXPRESSION_REFERENCE_MISSING`. **Where this departs from After Effects on purpose:** `value + 5` on a position is an error rather than a surprise; an expression reading its own property through `thisLayer` is `EXPRESSION_CYCLE`, where After Effects quietly gives the keyed value; `valueAtTime` reads whole frames only, which is D-58's no-shutter rule; a wiggle here is a wiggle of the same character and not the same numbers as theirs; and `ease` is a stated curve, because theirs is not published. **The fixture came before the code.** FX-EXPR-001 to 016 in document 25 are generated by `tools/expression_reference.py`, a whole reader and evaluator in Python written from document 09 and sharing nothing with the build, and `Fixtures/projects/expression_project.json` is the file both evaluate - nine layers and a wiggling camera. Documents 03, 07, 09, 11, 15, 19, 20, 24, 25 and 28 and the schema are amended, each marked proposed and now accepted. Document 21 is not: an expression changes a property's value and nothing about how a value is drawn. Document 26 is not either: setting an expression is an ordinary command with an ordinary inverse. Document 27 needs no change of rule, but B-14b must show that the effect cache is keyed on the evaluated values rather than on keys, since an expression makes a value change on a frame with no key. **Consequence if accepted:** B-14b builds the evaluator and the file round trip against these fixtures, with the export refusal; B-14c puts an expression box on each property in the window and shows its error there. **Consequence if declined, or changed:** the fixtures are rewritten before any code exists to argue with. **Not decided here:** `if`, comparisons and loops; `toWorld` and other space conversions; text layers and `sourceText`, which need a text layer first; expressions on effect parameters; a pick whip that writes a reference by pointing; and a translator for After Effects projects, which is level C of document 09's ladder and a separate decision.

D-61 / Collect and package: one folder that opens from anywhere, with a manifest of every file / ACCEPTED on 2026-09-16 by the owner ("accept d-61"), written by the agent as B-15a with its fixtures first. It answers R-14. **What is already there:** a project stores each drawing's path relative to the project file (document 07), Save As rewrites those paths for the new folder (B-13e), and a missing drawing is kept and reported as `MEDIA_MISSING`. **What is not there:** a way to hand a shot to someone else without copying the drawings by hand and hoping every path still points somewhere. D-62 / EXR in and out: the OpenEXR file read into the working buffer as it is, and written from it as it is / ACCEPTED on 2026-09-17 by the owner ("accept d-62"), written by the agent as B-16a with its fixtures first. It answers the first format of R-15, which D-60 made EXR by the owner's choice. **What is already there:** the working buffer is RGBA float32, linear light, premultiplied (document 21), and may hold colour below 0 and above 1. PNG stills and sequences come in and go out, and a drawing that cannot be read is kept and reported (`MEDIA_UNSUPPORTED_FORMAT`, `MEDIA_DECODE_FAILED`). **What is not there:** a way to take a render from a 3D or compositing program, or give one back, without squeezing it into eight or sixteen bits and losing everything above white. OpenEXR is that format, and its own convention - linear light, premultiplied - is the working buffer's, so no colour conversion is needed in either direction. **Coming in.** `media.import` and `media.relink` accept `.exr` beside `.png`; the extension decides which reader is used, and stills and numbered sequences work exactly as they do for PNG, gaps included. An EXR drawing's interpretation is `linear-srgb`, premultiplied, and is never guessed from the file. **The picture is the display window**: the drawing's size is the display window's, its top-left pixel is the display window's top-left corner, and wherever the data window does not cover it the drawing is transparent black. Samples outside the display window are cut off. **Channels,** matched exactly, capitals included: if the file has any of `R`, `G`, `B`, those are the colour, and a missing one is 0. Otherwise, if it has `RY` or `BY`, it is refused, because colour-difference files need a conversion this entry does not specify. Otherwise, if it has `Y`, then R, G and B are all `Y`. Otherwise it is refused. `A` is the alpha, and 1 where there is no `A`. Every other channel - depth, a render layer such as `diffuse.R`, a `Y` beside RGB - is not used, and is reported. Half and float samples are used as they are; whole-number samples become the float of the same number. **Values** below 0 and above 1 in colour are kept. A sample that is not a number or is infinite becomes 0, and then an alpha below 0 or above 1 is clamped into 0 to 1, because document 21 defines alpha as coverage. **Reported, not refused:** a new WARNING, `MEDIA_EXR_ADJUSTED`, says that a file was drawn but not exactly as stored, with one reason for each thing done: `channels_ignored` (naming them in the file's order), `outside_display_window` (how many pixels were cut off), `non_finite` (how many samples became 0), `alpha_clamped` (how many), `pixel_aspect` (a pixel aspect ratio other than 1: drawn with square pixels) and `primaries` (a `chromaticities` attribute that is not Rec. 709: drawn with its numbers unchanged, which is right only if the composition's other drawings share those primaries). A file with none of these is drawn with no report. **Refused** with `MEDIA_UNSUPPORTED_FORMAT`, the asset kept, and the reason named: more than one part (`multipart`), deep data (`deep`), HTJ2K compression (`htj2k`), channels stored at less than full resolution (`subsampled`), colour difference (`luminance_chroma`) and no colour channel at all (`no_colour_channels`). A file that is not EXR, is empty or is cut short is `MEDIA_DECODE_FAILED` (`unreadable`). The refusals are decided from the header before any pixel is decoded. **Going out.** `export.sequence` gains a format choice, PNG or EXR, and for EXR a sample choice, half (the default) or float. Each frame is `<name>_<frame>.exr`: one part, scanlines, top to bottom, channels `A`, `B`, `G`, `R`, ZIP compression, data window and display window both the composition's size at the origin, pixel aspect ratio 1, screen window centre (0, 0) and width 1, Rec. 709 `chromaticities`, and `framesPerSecond` as the composition's rate, a fraction. Nothing else but the `chunkCount` the format itself may add: no dates, no program name, no paths, so the same frame written twice is the same file. **The samples are the working buffer's, unchanged and premultiplied**, so the straight-alpha choice is not offered for EXR. Float is exact. Half is the working value clamped to -65504 to 65504, half's range, then rounded to the nearest half, ties to even: that is the declared encoding step of document 21 and has no diagnostic, as PNG's rounding has none. The missing-drawing choice is the same as PNG's. **The library.** OpenEXR's compressions are many - ZIP, PIZ, PXR24, B44, DWA - and each is a codec of its own. **This entry recommends the `exr` crate, version 1.74.2, with its default features off**, which reads all ten compressions in the fixtures and writes ZIP. It is BSD-3-Clause and brings 14 packages this build does not have yet, all MIT, Apache-2.0 or BSD-3-Clause (B-16b counted 15: `bytemuck` also came, under Zlib, Apache-2.0 or MIT, and two of the 15 ship no licence text, as `Licenses/` records); B-16b records them in `docs/DEPENDENCIES.md` and archives their licences, as every dependency is, and ADR-007's "revisit when EXR handoff arrives" is answered by this entry. It was measured before this entry was written, in a scratch program outside the build: it reads every fixture file whose windows match to the last bit of the reference, DWA and B44 included, so **no tolerance is proposed**; files it wrote passed the export check, 60 of 60; and it does not decode HTJ2K itself, which is one more reason that refusal is made from the header. **The alternative,** if the owner would rather not take the dependency: the build writes its own reader and writer for the uncompressed, RLE and ZIP kinds, using the ZIP code it already has, and refuses PIZ, PXR24, B44 and DWA with `MEDIA_UNSUPPORTED_FORMAT`. Those four are common in renders from other programs, so that would refuse many real files. The fixtures do not change either way; only which ones a build must draw. **The fixture came before the code.** `tools/exr_reference.py` writes every test file with OpenEXR's own library, reads each back with it and applies this entry's rules in Python, sharing nothing with the build; it also checks files the build exports, with the same library. FX-EXR-001 to 010 in document 25 are its tables, and `Fixtures/exr/expected_exr.json` holds every expected pixel. Documents 03, 07, 11, 15, 18, 21, 24, 25 and 28 are amended, each marked proposed. Document 19 and the schema are not: an EXR asset is an asset with a different file, and its interpretation values already exist. Document 26 is not: import and export are ordinary commands. **Consequence if accepted:** B-16b adds the dependency, the reader and the writer, with a generated table walking FX-EXR-001 to 010, which is T-14 for EXR, the export half quoting `tools/exr_reference.py check`. B-16c adds `.exr` to the file dialogs and the format and sample choices to the export dialog, with a playtest sheet that opens an exported frame in another program. **Consequence if declined, or changed:** the fixtures are rewritten before any code exists to argue with. **Not decided here:** choosing a part or a render layer from a multi-layer file; deep data; colour-difference and subsampled files; turning primaries or pixel aspect into a conversion rather than a report; writing other compressions, tiles, or several layers at once; timecode and other metadata; and WAV, which D-60 leaves until a shot needs it.

D-69 / Separate X and Y for position, and auto, continuous and roving keys / PROPOSED on 2026-09-18 by the agent as B-19e, with its fixtures first. **ACCEPTED on 2026-09-18 by the owner ("proceed").** They are items 7 and 10 of the scope the owner gave B-19 on 2026-09-18 ("all 10 please"). **What is already there:** a key carries one ease for the segment that starts at it (D-52), and a position key may carry path handles (D-53). Both of a position's numbers take the same ease. Every key is what After Effects calls a plain bezier key: its two sides are set apart, and nothing keeps them smooth when a neighbour moves. **Separate dimensions.** A layer's position may be written `{"x": property, "y": property}` in place of `{"base", "keyframes"}`: two properties of one number each, with their own keys, eases, kinds and expressions. The position at a frame is `[x at the frame, y at the frame]` (FX-SEP-001, 002), and everything that uses a position, the transform, parenting, the camera's view of it, takes that pair as before. A separated position has no path handles, which is After Effects' rule as well: a path is one curve through pairs, and X and Y apart are two curves against time. `property.separate` on a position turns each of its keys into a key of X and a key of Y on the same frame with the same ease and kind, and drops the path handles and roving (FX-SEP-003); it is refused while the position has an expression. Used again it joins them: a key wherever either had one, holding the position at that frame, with X's ease where X had a key and else Y's (FX-SEP-004), which keeps the keys and can lose the shape between them when X and Y were eased apart; Undo brings it back. Commands name the two as `position_x` and `position_y`. **A key's kind.** A key gains `"kind"`: absent, which is today's key; `"continuous"`; or `"auto"`. **Neither changes how a frame is worked out.** The file always holds the eases that are rendered, and the kind says what an edit must keep true of them. The measure is the speed the Keyframe Velocity box has shown since W-25: out of a key, `y1 / x1 * L / frames`, and into it, `(1 - y2) / (1 - x2) * L / frames`, where L is how far the value goes over that segment: the difference for a number, signed; for a pair the straight distance, or three times the path handle's length at that end. **Continuous:** the speed in equals the speed out. Making a key continuous, or moving it or a neighbour, sets both sides to the mean of the two speeds, each handle keeping its length (FX-KIND-005); pulling one side by hand makes the other follow it (FX-KIND-006). **Auto:** both handles are a third long and both speeds are `(L_in + L_out) / (next frame - previous frame)`, the slope between the neighbours (FX-KIND-001, 003), worked out again whenever the key or a neighbour changes (FX-KIND-004); the first and last keys leave and arrive as a straight line (FX-KIND-002). Pulling an auto key's handle by hand makes it continuous, as After Effects does. A side that is a hold, or whose value goes nowhere, has no speed to set and is left alone (FX-KIND-007): this build's ease is a fraction of the way between two values, so a segment between equal values stays flat, where After Effects' value graph could bulge it. Making a key auto or continuous turns a linear segment beside it into the ease that is the same line, `[1/3, 1/3, 2/3, 2/3]`, so there is a curve to set. **Roving.** A position key that is not the first or last, and not separated, may carry `"roving": true`. Its frame is then worked out: across a run of roving keys between two keys that are not, each sits where it would fall if the run's path were travelled at one speed, `first frame + frames * (length so far / whole length)`, rounded to the nearest frame, halves up, and then moved so no two keys share a frame and none leaves the run (FX-ROVE-001, 002). A straight segment's length is the distance; a curved one's is measured along 64 straight pieces at equal steps of D-53's parameter (FX-ROVE-004). The frames are worked out again when a value, a path handle or either end key of the run changes; an edit that leaves a run fewer frames than it has roving keys is refused with `COMMAND_INVALID_VALUE` (FX-ROVE-003). Roving places the key and leaves every ease alone. Dragging a roving key in time by hand stops it roving, as After Effects does. The file holds the frame that resulted, so a reader never works it out. **On reading a file** nothing is recomputed: `kind` on any key and `roving` on a position key are kept, `roving` anywhere else or on a first or last key is `PROJECT_SCHEMA_INVALID`, and so are path handles or a pair's keys inside a separated position. **Commands** (document 24), to be built in B-19f: `property.separate`; `keyframe.set_kind` with `kind=bezier|continuous|auto`; `keyframe.set_roving`; each over every chosen key as one entry to undo. **The window**, B-19g: the three kinds and Rove Across Time in the key menu, with After Effects' key shapes on the timeline; Separate Dimensions on the position's menu, after which the inspector, the timeline and the graph show X Position and Y Position as properties of their own, which is what gives X and Y separate handles in the graph. **Not proposed:** separating the camera's place, the anchor or the scale; a handle that bulges a flat segment; roving at an exact arc length or at a speed the end keys' eases shape across the run; roving on anything but position. **The fixture came first:** `tools/keykind_reference.py` works every case from the formulas above and checks each against a value worked by hand; document 25's FX-SEP-001 to 004, FX-KIND-001 to 007 and FX-ROVE-001 to 004 are its output, with the two separated projects in `Fixtures/keykind/`.

D-73 / Export choices: three MP4 qualities, GIF dithering, the MP4's colour label, and the list says which files are lossless / PROPOSED on 2026-09-19 by the agent as B-22a, with its fixtures first, at the owner's word ("write D-73") after they asked for "a raw export of gif/mp4/animated png and selectable levels of compression/bitrate and color space" and for a recommendation. **ACCEPTED on 2026-09-19 by the owner ("accept D-73, proceed with B-22b and B-22c").** It was written that nothing is built against it until the owner accepts it. **Raw.** A lossless export already exists for everything that can have one: the PNG sequence and the animated PNG keep every value, and EXR is the full-precision master. A GIF cannot be raw, because 256 colours a frame is the format; H.264 through the encoder Windows carries has no lossless mode. So no "raw" choice is added; the list beside Export says which entries are lossless. **MP4 quality.** Three named levels, Preview, Standard and High: 0.1, 0.2 and 0.5 bits for every pixel of every frame, floored to whole bits a second and kept between 1 and 100 megabits (FX-FMT-040). Standard is what B-21d writes today. Flat cel colour is where a low bitrate shows blocks, which is what High is for. No free number box: a number nobody can judge invites films that look wrong with no sentence to explain why. The same rule on both D-30 roads. What the fixture holds is the number asked of the encoder; the size of the file depends on the picture and is not a fixture. **GIF dithering.** One choice, on or off, off being what B-21c writes today. On is Floyd and Steinberg's error diffusion in whole numbers, so that two programs agree to the pixel: a see-through pixel takes no error and passes none on; ties go to the first palette colour (FX-FMT-050 to 052, on fixed small palettes, because the palette `color_quant` picks cannot be reproduced by an independent program). D-73a / GIF dithering: the carried error is held within limits, to end the coloured specks / PROPOSED on 2026-09-19 by the agent, with its fixtures first, at the owner's word ("B-22c playtest passes; write the D-73 amendment for the specks"). **ACCEPTED on 2026-09-19 by the owner ("accept D-73a, proceed with B-22d")**; FX-FMT-050 to 052 are retired by it and stay in the fixture file, marked so, as the record of D-73's first rule. It was written that nothing is built against it until the owner accepts it. **What was seen.** D-73's dithering passes on the whole difference between the colour wanted and the colour spent. Where the 256 colours have nothing near (the dark trunk, the deep pink of the tree, the grey of the cloud), the difference builds up pixel after pixel until it is large enough to land on a far, bright colour: red dots in the pink, yellow in the trunk, orange in the cloud. **The amendment, two steps added to the rule and nothing else changed.** One: the pixel plus its carried error is held within 0 to 255 before the nearest colour is looked for. Two: the difference is held within plus and minus 16, in each of red, green and blue, before it is shared out 7, 3, 5 and 1 sixteenths. See-through pixels, ties and the flooring are as D-73 has them. **Why 16.** The agent tried the rule in Python on a piece of a real frame of the reference shot, with the 248 colours `plain.gif` uses: `verification/D-73a proposal/as_accepted_against_proposed.png`, D-73 on the left, this on the right. Counting pixels that land further than 80 (of 255, straight-line distance in red, green and blue) from the colour they should be: 805 as accepted; 190 with step one alone; 46 with a limit of 32; none with 16. The sky's bands stay gone at 16. This is the agent's trial, not the build, and one frame of one shot. **What it gives up, stated.** With only a few far-apart colours to spend, dithering can no longer mix them: a mid grey in black and white alone would come out one flat colour, not a checker. A GIF from this program always has up to 256 colours picked from the picture itself, so that case does not arise in an export; it is exactly what FX-FMT-050 to 052 test, so on acceptance those three are retired and FX-FMT-053 to 055 replace them. A large area of a colour the palette lacks becomes its nearest colour, flat, instead of that colour with bright dots (FX-FMT-055 shows both). Evidence basis: `Fixtures/formats/expected_formats.json`, cases FX-FMT-053 to 055 from `tools/formats_reference.py`, insertions only; document 25 shows them. Consequence if accepted: B-22d, a few lines in `dither_indices`, the table walks 053 to 055 in place of 050 to 052, a new `dithered.gif` and side-by-side picture for the owner's eye. D-74 / Solid layers: a layer that is a rectangle of one colour / PROPOSED on 2026-09-19 by the agent as B-23a, with its fixtures first, at the owner's word ("go, yes to all three; proceed with B-23a"). **ACCEPTED on 2026-09-19 by the owner ("accept D-74, proceed with B-23b")**; B-23b builds it in the core. It was written that nothing is built against it until the owner accepts it. **The layer.** A new layer kind, `solid`, whose drawing is a rectangle of one colour, as After Effects' solid is. It has no `asset_id`, no exposures and no source offset. It carries a `solid` record of three things: `color`, three numbers from 0 to 1, red, green and blue in the working space (linear, as the tint effect's colour is); `width` and `height`, whole numbers of pixels from 1 to 8192. Everything else a drawing has it has, and it means the same: name, switch, lock, in and out frames, transform, opacity, mask, matte (it can shape another layer and be shaped by one), parent, depth, label, shy, blend mode (all of them, unlike an adjustment layer) and its effect stack. The colour and size are not animated. **Its picture.** Document 21's step 1 for a solid is not a decode: it is `width` by `height` pixels, every one the colour, opaque, in its own layer space with (0, 0) at its top left. Steps 2 to 7 then run on it exactly as on a drawing: the mask and the effects in its own space, then the transform, parent and camera, matte, opacity and blend. So a solid and an opaque drawing of the same colour and size give the same frame. **A new solid** is the size of the composition, with its anchor at its own centre and its position at the composition's centre, so it covers the frame exactly, and is named `Solid 1`, `Solid 2` and so on. Changing its size keeps its anchor at the same fraction of its width and height, so a centred solid stays centred, and is one step of history. **The colour in the window** is chosen with the system's colour picker, which works in the 256 levels of the screen: the choice is turned into linear by document 21's sRGB curve and stored so, and the picker shows the stored colour by the same curve back. A colour written into a file by hand in between two of the 256 levels is kept exactly and drawn exactly; the picker shows the nearest level. **Refused.** A file whose solid names an asset, has exposures or a source offset, has no `solid` record, has a colour that is not three numbers from 0 to 1, or a width or height that is not a whole number from 1 to 8192, is `PROJECT_SCHEMA_INVALID`, and so is any other kind of layer carrying a `solid` record (FX-SOL-020 to 029). No build writes any of them. **Commands.** `layer.add_solid`, above the chosen layer or else at the front, Ctrl+Y as in After Effects, with an optional colour, width and height; `solid.set`, the colour, width and height of one solid, one step of history. Both refuse a value outside the ranges above with `COMMAND_INVALID_VALUE`, in a sentence. **Nothing to fetch.** A solid has no media: it is never missing, collecting a package has nothing of it to copy, and it draws the same on every machine. **Ceiling, stated.** A solid is drawn whole, as a drawing is: one of 8192 by 8192 takes a gigabyte while it is drawn. After Effects allows 30000; 8192 is twice a 4K frame each way. Evidence basis: `Fixtures/solid/`, FX-SOL-001 to 008 (frames) and 020 to 029 (refusals), from `tools/solid_reference.py`, which renders each pixel from document 21 and moves by whole pixels only; document 25 shows them. Consequence if accepted: B-23b, the kind in the core and the file, its picture, the refusals and the two commands, with a table that walks FX-SOL-001 to 029; B-23c, the window: New Solid in the Layer menu, the colour and size in the layer's panel, and a playtest sheet.

D-76 / A solid's colour and size over time / PROPOSED on 2026-09-19 by the agent, from the owner's question at the B-23c playtest ("have width and height be drag click as well, maybe keyframeable?"). The drag was window work and is built; keying is not, because D-74 says in as many words that a solid's colour and size are not animated, and that is what the file, the schema and `Fixtures/solid` were written to. **Nothing is built against this until the owner accepts it.** **What it would mean.** `color`, `width` and `height` would stop being three plain values in the `solid` record and become three of document 19's properties, each with a base and its own keys, drawn on the timeline with a stopwatch like Position and Opacity. **What follows.** The file changes shape, so every project written since B-23b would be read by a rule that takes the old shape as a base with no keys (no fidelity is lost, but the conversion has to be written down and walked in a table). D-77 / What a mask is, from B-24 on / PROPOSED on 2026-09-19 by the agent, as B-24a, from D-75, which the owner accepted on 2026-09-19 ("masks with the pen and feather next"). **Nothing is built against this until the owner accepts it.** **The shape in the file.** A layer's `mask` becomes `masks`, a list, in the order they are drawn, first to last. Each holds a `name` ("Mask 1", "Mask 2" and so on), `enabled`, `inverted`, a `mode` of `add`, `subtract`, `intersect`, `difference` or `none`, an `opacity` from 0 to 1, a `feather_px` of 0 or more, an `expansion_px` from -8192 to 8192, and a `path`. The path is a document 19 property from the start - `{"base": {"points": [...]}, "keyframes": []}` - so that B-24d only has to fit a stopwatch to it and the file never changes shape twice. A point is `{"point": [x, y], "in": [dx, dy], "out": [dx, dy]}`: the two handles are offsets in pixels from the point, which is D-53's convention for a path, and a handle of `[0, 0]` means no handle. A mask is closed by definition, as document 19 already says; open paths are B-25's business, not a mask's. **What is kept exactly.** A segment whose two handles are both zero is one straight line, and an expansion of zero touches no distance arithmetic at all, so every mask written before this decision draws pixel for pixel what it draws today: same 4x4 grid, same even-odd rule, same sixteenths, ADR-016 unamended. FX-MSK-001 is that claim as a fixture. A file with the old single `mask` key is read as one mask, mode Add, opacity 1, feather 0, expansion 0, every handle zero, `enabled` and `inverted` as it held them, named "Mask 1" (FX-MSK-002); saving writes `masks` and no `mask` key, so a project saved by this build and opened by one older than it loses its mask - which is why a file holding both keys is `PROJECT_SCHEMA_INVALID` rather than a guess (FX-MSK-020). **The curve.** A curved segment is a cubic Bezier through the two points and the two handles, flattened into `n` straight pieces at equal steps of t before the sampler ever sees it, where `n` is the control polygon's length in pixels halved and rounded up, held between 16 and 512, the length summed point, out handle, in handle, point in that order so the count is the same on every machine. Flattening before sampling is what keeps one rasterization rule in the build instead of two. Known ceiling: a curve longer than about 1024 pixels is flattened to pieces of more than 2 pixels and will show it; raising the 512 is an amendment to this decision and changes every fixture it touches. **One mask's own coverage, in this order.** Expansion first: a sample point is inside when its distance to the outline, signed positive within, plus the expansion is zero or more, so a corner rounds off exactly as After Effects rounds one, and a negative expansion shrinks. Then feather: document 21's Gaussian on the coverage alone, separable, normalised, radius `ceil(3 * sigma)`, with `sigma = feather_px / 2`, so a feather of 4 pixels is a band of about 4 pixels; the coverage outside the frame is worked out like any other coverage rather than invented, so a mask against the frame's edge does not darken. Then invert, which is `1 - m`. Then opacity, which multiplies. **Several masks.** The accumulated coverage starts at nothing, except that a first mask in Subtract or Intersect starts from the whole layer, because there would otherwise be nothing to take away from and such a mask could only ever give an empty frame - this is what After Effects does and what an animator expects. Then, first to last: Add is `a + m - a*m`, Subtract is `a * (1 - m)`, Intersect is `a * m`, Difference is `a + m - 2*a*m`, each held within 0 and 1. A mask in mode None takes no part in the picture at all; it is there to be drawn on screen and pointed at. A layer with no mask that takes part is whole, as it is today. **What is kept and diagnosed rather than refused.** A mask of fewer than three points, or one whose points cross, is kept in the file, takes no part in the picture and raises `MASK_INVALID_OUTLINE`, exactly as today (FX-MSK-018, 019); document 28 asks for that rather than losing a project over one bad outline. The crossing test is on the points alone, as it is today - handles are not tested, and a curve that crosses itself is drawn by the even-odd rule, which is defined for it. Known ceiling: the test stays the O(n^2) pair scan `src/mask.rs` already carries its own note about. **What is refused whole**, as `PROJECT_SCHEMA_INVALID`: both keys at once, an unknown mode, an opacity outside 0 to 1, a feather below 0, an expansion past 8192, a point or handle that is not two numbers, a mask with no path, a `masks` key that is not a list, masks on an audio layer (D-71, unchanged), and a keyed path whose key holds a different number of points from its base. That last is the animated-path rule stated now and built in B-24d: a path is interpolated point by point, point and both handles, between keys that hold the same number of points, by document 20's curves; adding or removing a point on a keyed path is a command's problem, not a file's. **Where it sits.** Document 21 step 2 is unchanged in place and in space: the masks are applied to the layer's own picture, in layer space, before the effects and before the transform, the accumulated coverage multiplying premultiplied RGB and alpha together. Masks are still not inherited through parenting. **What it costs.** Feather is a blur of the coverage field over the layer's own bounds plus the blur radius, per mask, per frame; expansion needs the distance to the outline at every sample, which is the flattened outline's length times sixteen samples a pixel, and is the expensive half of this decision. Both are named here so that B-24b's table can record them rather than discover them. **Evidence.** `tools/mask_reference.py` and `Fixtures/masks/`: FX-MSK-001 to 019 frames within 1e-6, FX-MSK-020 to 030 refused; drawn in `verification/B-24a proposal/mask_cases.png`. Consequence if accepted: B-24b the core, B-24c the window, B-24d animated paths, and document 19, the schema and ADR-016's surrounding prose amended to match at B-24b.
