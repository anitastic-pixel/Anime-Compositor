# P-16: what each effect costs, before and after the blur's rewrite

**The Gaussian blur, and the Glow built on it, are up to 7x faster, and no pixel of any effect moved: all 24 results below have the same SHA-256 before and after.** A Glow of radius 250 on a character cel went from 228.1 ms to 33.3 ms; a blur of 40 on a character cel from 96.1 ms to 15.2 ms.

Asked for by the owner on 2026-09-25 ("improve overall performance of the effects"), after the B-33c playtest used a Glow of radius 250.

## Machine, build and configuration

- CPU: AMD Ryzen 9 9900X, 12 cores, 24 hardware threads
- OS: Microsoft Windows 11 Education, 10.0.26200
- Toolchain: rustc 1.89.0, cargo release profile, `opt-level = 3`
- Pool: rayon's default, one thread per hardware thread
- Harness: `tests/p16_effect_cost.rs`, run with `cargo test --release --test p16_effect_cost -- --ignored --nocapture`
- Before: commit 86d4b00. After: the commit that carries this page. The same harness, run once on each, the same day.
- Workload: one effect alone on a 1920x1080 cel, 7 runs each, median reported. Two cels, both generated by the harness: **character**, a figure in flat colours on nothing, about a fifth of the frame showing; **background**, opaque everywhere.

## What changed

Only the Gaussian blur's inner loop, `convolve` in `src/effects.rs`, which the Glow uses for its spread. It used to work one destination pixel at a time, checking every tap against the edges. It now adds each tap along a whole row at once, which the compiler turns into wide instructions, and it skips any part of a row that is all zeros, which a character cel mostly is. Each pixel still starts at zero and receives the same taps in the same order, so the sum is the same to the bit; `the_row_blur_is_the_pixel_blur` in `src/effects.rs` holds the new loop to the old one, bit for bit, over cels with empty rows, lone pixels at the edges, negative and huge values and a buffer narrower than the kernel. Every fixture table in `verification/` that the test suite writes came out byte-identical except the two that gained a check (below).

A second attempt, working the vertical pass in 64-pixel strips to keep its rows in the core's cache, measured no better (Glow 250 on the character cel 40.9 ms against 32.0) and was taken out.

## What was not made faster, and why

- **Selective Colour Blur, 43 to 89 ms.** Each chosen pixel walks up to its reach on both sides and stops at the first unchosen pixel, which is the rule D-87 ported; the walk has no shortcut that keeps the bits. The effect-result cache (P-11) holds it between frames when it is not being dragged.
- **Glow 250 on an opaque plate, 96.6 ms.** Everything bright glows, so there are no zeros to skip, and 501 taps a pass over a 2420x1580 buffer is the arithmetic itself. The next step would be building for the machine's wider instructions (`target-cpu`), which changes no pixel but makes the build only run on processors that have them; that is a decision, not a fix.
- **Exposure, Tint, Line Smoothing**: 1 to 12 ms already.
