# ADR-013: Verification by fixtures and artifacts, not code review

Status: ACCEPTED
Date: 2026-09-04
Deciders: Andrew (owner)

## Context

The version 0.2 process documents assumed a human reviewer reading diffs. The owner has no programming background. That reviewer does not exist and cannot be created.

This is the most consequential fact about the project, and it was discovered during version 0.3 planning rather than at the start.

## Decision

Human source code review is removed from the quality system entirely and is never assumed as a backstop. It is replaced by five mechanisms.

Independent fixtures. Expected values are derived from reasoning about correct behavior, never generated by the implementation under test.

Fixture integrity. Expected values in `Fixtures/` and document 25 are read-only to implementation work. Changing one is a specification proposal requiring owner approval, submitted separately, never bundled inside a task that is otherwise reporting success.

Mandatory verification artifacts. Every completed task produces something a non-programmer can judge: fixture tables with expected versus actual, exported images, screenshots, project files.

Mandatory not-run reporting. Every report states what was not run and why.

Render trace. The renderer can dump intermediate layer buffers as images, so wrong output becomes a looking problem rather than a reading problem.

## Rationale

An agent that cannot be checked will eventually take the path of least resistance: weakening a test, generating an expectation from its own output, or reporting a success it did not measure. None of that requires bad intent. Without a control, it is invisible.

The fixture integrity rule is the load-bearing part. Every other mechanism can be satisfied superficially. A locked expected value cannot.

## Consequences

Specification work becomes the main job of the owner and the bottleneck of the project. Fast code generation does not reduce it, which is the counterintuitive part and the thing most likely to be forgotten later.

This protocol catches wrong results. It does not catch bad architecture, accumulating internal complexity, or security weaknesses that never surface as a failing fixture. Those risks are accepted knowingly and mitigated only by keeping scope narrow and module boundaries intact. Recorded as K-04 and permanently open.

If external engineering review ever becomes available, spend it on architecture and safety, not on correctness that fixtures already cover.

## Alternatives considered

Learning to program well enough to review a compositing engine is a multi-year path and is not a plan.

Paying for review is outside the budget, and open-source distribution means there is no revenue to fund it.

Trusting reports without artifacts was rejected as equivalent to having no control at all.
